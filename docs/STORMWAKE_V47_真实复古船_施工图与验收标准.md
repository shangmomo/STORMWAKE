## 2. 坐标统一——严禁再次靠非等比缩放蒙混

- 输入的 Blender：+Z 为上、Y 为船长轴。GLB 导出：+Y 为上，+Z 为前后主轴，+X 为左右舷。所有网格单位按 1 m 解释。
- 美术船壳处于独立 `ArtistShip` 根节点；现有 `ShipPhysicsRoot` 是动力学唯一权威，船舱、站点、物品保存 ship-local 坐标。不能让输入、视觉、库存各自维护独立「船的位置」。
- V47 为过渡兼容只做一次显式美术对齐：`scale (1.064, 0.75, 1.064); offsetY=-1.2m; offsetZ=-0.70m`，且用反向变换抵消老的 heritage 船比例。**后续应在 Blender 以统一目标 1:1 坐标重新导出**，避免把这个过渡变换长久埋进碰撞与物理。
- 将主甲板、下层甲板、货舱地板、两舷墙和舱口边缘生成为可检查网格，walkmesh 与绘制模型共用同一 GLB 源坐标。建立可视化 debug 模式，可叠加玩家胶囊体、接触法线、货物可摆位盒。

## 3. 主船结构施工图：不是空壳，也不是一个大方盒

**目标约束：** 船体 L≈22m，B≈5.2m。以真实几何为约束，宁可局部收窄、调整舱内隔舱，也不凭空把船舱做成比船壳更宽的矩形。如下区间是施工参考，不是已经测得的可通行净尺寸。

| 船内分区 | 应用 | 必须布置的可见/可操作物件 | 关键约束 |
|---|---|---|---|
| 船首甲板 | 望远镜、系泊、抛锚、登船 | 主锚机、绳索、前帆操纵位、前梯 | 不允许因为模型前甲板抬高而踩空 |
| 中央主甲板 | 双舷炮位与甲板搬运 | 舵/帆对应控制、4 门以内火炮、桶、舱口、围栏 | 操舵和装炮状态分离，炮口不会穿船壳 |
| 后甲板/尾楼 | 航图、船钟、罗盘 | 地图桌、灯、日志、舵轮 | 相机撞击后不透视穿进尾楼 |
| 主甲板下层 | 货物、修船、储物 | 可见货架、炮弹架、木板架、两排可摆箱位 | 玩家通过连续楼梯/梯子进入，禁止瞬移楼层 |
| 舱底/舭舱 | 进水、破口定位、排水 | 局部破口、水位标尺、水桶、抽排点 | 室内水面独立于外海；无破口时绝不自动出现海水 |

**建模必须补齐**：真正的船体内壁（有厚度）、甲板上下两面、挡水舱壁、可打开舱口、连续梯子扶手、炮窗/炮门、碰撞面。要求船舱墙体与外壳无明显间隙或重叠面；装饰件不应参与高复杂度碰撞。

**洞口处理**：本轮已从原船壳甲板三角形中切除目标洞口范围，防止玩家从梯子上方看到一块没有打洞的假甲板；这**不**表示内部楼梯已经与船壳精确严丝合缝。正式版必须重新拓扑形成四边框、甲板板材截面与洞口护栏，并做站立/蹲行空间测量。

## 4. 绝不穿模的物理和相机约束

### 4.1 物理表示层

使用五层不同几何，不能拿一块船壳三角网格包办：
1. **WaterlineHull**：近水线采样与浮力，可用 12–20 个船体点 + 垂向体积近似，随俯仰横摇更新；与模型同一实际尺度。
2. **WalkMesh**：甲板/舱底/梯子/楼梯分片，包含坡度、台阶高度、边缘与区间层级标签。
3. **CollisionShell**：静态船侧、横隔、桅杆、舱壁合并成低多边形凸体/盒体集合；统一变换到船本地坐标。
4. **InteractVolumes**：可按交互状态开关的触发范围，如舵轮、炮尾、箱子、储物桶。
5. **CameraOccluders**：第一/第三人称镜头 sweep sphere，命中后缩短相机臂；船舱第一人称为默认，不能用任意世界坐标穿过船壳。

### 4.2 碰撞精度与自测

- 玩家胶囊半径建议 0.28m、高度 1.70m。玩家移动执行 swept capsule / substep 与接触解算，不用位置 `clamp` 代替三维碰撞。
- `deck_y(x,z)` 从实际可行走三角形投射，不能由单个旧标量 `deckY` 代表整船；人物随刚体移动且保留相对速度。
- 在翻滚 ±12°、俯仰 ±8°、全速回转、进出梯子、拾取箱子时，脚底相对甲板间隙目标 ≤ 0.04m；只容许碰撞形状的有限接触误差，不允许突然穿过墙面或瞬移至海水下方。
- 高速船体旋转时以固定 timestep 为物理权威，渲染插值；角色与放下的货物都必须跟随 `ShipPhysicsRoot`，不能依赖每帧重写世界坐标。
- 验收必须录制：第三人称从尾楼走至船首、下舱到货架，再回甲板；每 10 秒触发一次暴风船摇；按 10 组不同镜头 FOV 重测。

## 5. 船舱不再“装满海水”的渲染与损伤设计

- 外海水面是单一连续 OceanFFT 水面，但**不能**出现在干燥船舱内。必须使用从真实船壳/舱口构建的 boat interior stencil 或深度 mask，对 `WaterSurface` 做船内体积裁剪；禁止简单把全场海面关闭，导致从舱口看外海消失。
- 室内有单独 `BilgeWaterSurface`，只从 `ShipDamage` 的真实舱室水量计算 `height`，按舱段面积和体积曲线换算。初始 0% 的舭舱不可见水。
- 破洞局部实体记录 `(compartmentId, localPosition, radius, pressureFlow, state)`；涌水量应随洞口距世界水线的压强头变化。木板补洞后停流，但原有积水必须用桶排出。
- 太阳光、水下蓝绿后处理、体积雾、声源和火光分别受 `isInsideShip` 约束；室内摄像机眼点低于外海水平线不等于角色在海水下。
- 船沉没时依破口、隔舱与姿态渐进浸水，不能仅把 `ShipDamage.water` 变大就让木纹整片变蓝。
- 必须留透明/反射调试开关：show mask, show interior bounds, show compartment level, show scene depth；用水线上下各 0.25m 的摄像机截图做视觉验收。

## 6. 每个物品必须是真实体：拿取、摆放、存取

**统一实体结构**：`itemId / type / mesh / localTransform / parentShipId / ownerPlayerId / inventorySlot / mass / collision / interactionRadius / isPersistent`。网络与本地存档不允许双重副本。

**交互优先权**：从输入设备到 `InputContext`（World / Inventory / Helm / Sail / Cannon / Carry / Ladder / UI）只路由一条命令；当打开日志或菜单时禁止向驾驶发指令。同一 E 键只执行 raycast 命中的一个目标，并展示明确的名称和距离。

**物品状态机**：`WORLD → TARGETED → HELD → PLACING → WORLD/STORED`，含占用、冷却与失败原因。放下必须在合适的 deck/support mesh 上重新做碰撞；货物进入舱底不能像存入字典后消失。

| 物品 | 真实操作要求 | 检验用例 |
|---|---|---|
| 水桶 | 空桶可装海水/舱底水，满桶可泼海或灭火，内容物决定动作 | 无水空桶不能“泼水成功”；从舱底舀水后水位下降 |
| 普通炮弹/链弹 | 从弹药桶提取、持有、装入炮膛、扣减库存 | 手中未持炮弹不能装弹；一次发射只扣一次弹 |
| 木板 | 从木板箱取出、持板到具体破口、连续钉补 | 不在破口附近时不能直接回血 |
| 宝箱 | 拾取、持握、放在甲板、放入舱底货架、再取出 | 船航行 100m、横摇 10°、切视角后不丢失不复制 |
| 望远镜、刀、灯 | 使用姿态、第一人称手部挂点、音效、打断状态 | 切换武器不自动触发舵/帆按键 |
| 火炮 | 取弹→装弹→点火→后坐→回位→重新装填；瞄准与炮口一致 | 弹丸从可见炮口出射，不穿船体；后坐和冷却实际可见 |

交互每次提交一个由服务器或本地主状态机决定的权威 transaction；无库存、距离不符、上下层错误、物品被占用时应显示拒绝原因。不能只更换显示模型就标记此项完成。

## 7. 复古木材、帆与索具的美术规范

- 统一材质：船壳主木材暖暗棕、铜件氧化、麻绳粗糙灰棕、帆布米黄且具粗糙纤维；默认写实风格略夸张的造型比例，借鉴《盗贼之海》的可读性而不直接复制专有贴图。
- 上传 4K 纹理已降为 2K 供运行时预览；高配选择 4K 仅用于近距离船壳、船长室等特写，以 GPU 帧时间决定，不盲目叠加。
- 重要构件以 Blender 分件并设置 pivot：舵轮、船锚绞盘、主帆、前帆、横桁、炮架、炮管、炮门、吊梯、舱盖、灯具和木桶盖。当前 V47 仅对整片帆作 reef 范围视觉映射，不具备细分布料和索具动画。
- 幽灵船必须具独立的残破帆、空洞、鬼火、雾边材质、甲板幽灵船员、炮击光/弹道、沉没溶解；不要仅把整艘船调成半透明绿。近景船的每一块破损都应可从不同角度读出。

## 8. 远洋世界：远离港口、有节奏而非扎堆

- 港区 0–800m：海况平稳，有基础任务、少量普通敌舰，禁止生成十艘幽灵船阻断航线。
- 外海过渡 800–1800m：风浪递增，可能有商船、海盗巡逻，岸线在视野后方渐远。
- 风暴走廊约 1800–3100m：云层显著变暗、浪高增大、雨幕能影响能见度，阵风有方向与频率变化；避险路线可读。
- 幽灵舰队约 2100–3200m：采用 3 个分离巡逻群（V47 已从模型层连接 Quaternius 敌船），侦察→警戒→增援→旗舰→撤离的战斗节奏；远处 ghost ship 用 LOD 和批渲染。
- 龙卷与外围大海 3000m 及以后：水龙卷源于真实移动天气单元，含飞沫底座、涡环、向心力、切向力和逃离条件；玩家应能通过操帆与修船摆脱，不能只有画面旋转。
- 生成器采用 Poisson/最小距离约束、事件冷却、单一遭遇上限和动态卸载。港区安全约束与主要航道交汇角不应出现舰队团堵。

**必须视觉联动**：天气强度输入一次，分别驱动 OceanFFT 的波谱参数、船体浮力、风向与帆力、雨、云顶/天空、闪电与雷声、水下可见度和湿船材质；严禁只修改 HUD 或雨量不改变可见风浪。最大风暴强度由可玩性约束，强浪仍允许完成一段航行；大风暴应可以从远处以云墙、浪花颜色和远雷提前识别。

## 9. 稳定性与性能预算

目标环境：Windows Chrome/Edge WebGPU、1080p/60 FPS 的中高档独显。该目标须以真实硬件测试，不能从 Node 逻辑测试推出。首帧加入模型加载进度、错误日志、fallback 按钮；加载中禁用交互避免岗位引用尚未生成。

建议预算（尚待 GPU 验证）：主船船壳+索具+帆 ~69k 三角面；近景幽灵船每艘采用精简网格、1k atlas；同类箱子/炮弹实例化；贴图预算不要重复为每艘幽灵船加载相同资源。场景 GPU 纹理大于显存预算时主动使用 LOD。雨和龙卷使用有限步长和贴图粒子结合，不允许因为美术需求把全部粒子升级为 mesh。

## 11. 可重复运行的命令与测试证据

- 运行工程：`python start_v44.py --no-browser`，然后在同一电脑的 Chrome/Edge 中打开 `http://127.0.0.1:5173/?stormwake=1&heritageShip=1`。默认普通船模式仍保留为回退。
- 静态模型及全面逻辑测试：`npm run test:v47`；测试结果只代表文件、数学、输入/网络逻辑等自动可检查部分。
- 新模型清单：`public/models/stormwake_v47/asset_manifest.json`；每个文件的 SHA256 可重新计算核对。
- 自动化 **不** 覆盖 GPU 着色器编译、近景船壳外观、移动角色接触稳定性、风暴体积质量；这些仍需要实机视频/截图才可以签字。
- 本轮尝试 Chromium headless WebGPU 浏览器访问 `http://127.0.0.1:5173` 时被运行环境策略阻断 `ERR_BLOCKED_BY_ADMINISTRATOR`；静态 HTTP 资源和模型文件能以 200 返回。此限制属于当前验收环境，而非代码已通过可玩画面验收。
