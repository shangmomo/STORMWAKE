# STORMWAKE V58 → V60：现有工程深度修复、物理重构与逐项验收设计规格

**版本**：设计基线 1.0｜2026-11-15  
**适用工程**：用户上传的 `STORMWAKE_V58_AUTOQA_VISUAL_COMPLETE(1).zip`  
**检测证据**：用户上传的 `AUTOQA_V58_results_20261114.zip`  
**交付类型**：工程修复设计文档（不是已经修复的游戏包）  
**技术栈**：当前工程为 JavaScript / 自研 WebGPU 渲染与场景系统 / Node.js WebSocket 房间服务 / Playwright AutoQA。**本计划不擅自替换为 Unity、Unreal 或 Three.js。**

> 阅读规则：`[确认]` 表示在提供的源码、录屏/截图、报告或本轮 Node 测试中直接成立；`[高风险]` 是基于代码结构及现象的待验证问题；`[建议]` 为本文件提出、尚未实现的技术方案。验收项是目标而非已经达成的事实。参数均为首轮设计建议，须经 WebGPU 实机测量调优。

## 0. 执行摘要与首要决策

本项目不缺少名义上的系统：存在真实原船 GLB、多个舱室、船锚/舵轮/帆索/舷炮、浮力、海水、海怪、远海风暴、任务、AI 船员与 4 人房间服务。然而玩家仍会把部分玩法感知为“假的”，原因主要在于**可交互模型、碰撞通道、状态机、动画事件、物理结果和多人复制没有形成可验证的闭环**。

**三条禁止绕过的工程原则：**（1）对象可见不等于能使用：每个交互对象须存在物理证据、状态变化、视觉/音频反馈和联机结果；（2）“不穿模”应由统一几何碰撞与舱室体积边界保证，不依赖隐藏物体、瞬移和改变全场景可见性来掩盖；（3）AI/自动化不可把逻辑 PASS 等同于用户真实游玩 PASS，必须在真实浏览器里完成多角色路径和帧序列验证。

**第一轮只做 P0 纵切片**：从码头走上现有荷兰船 → 进入并退出船长室和下层货舱 → 四人可在同一绞盘上协同起锚 → 拉帆、转舵、船实际离港 → 发炮破坏船体 → 真实进水、修船和舀水 → 返港停泊；直到这个闭环稳定，不在主线增加全新大 Boss。

## 3. 基础架构：四层一致性契约

### 3.1 单个实体的完整定义

每个世界对象都有五个明确部分：`AssetInstance`（视觉模型与骨骼）、`PhysicsBody / ColliderSet`（碰撞体）、`Interactable`（使用范围和授权）、`AuthoritativeState`（玩法状态、归属、序列号）、`Feedback`（动画、声音、粒子、相机）。不可存在仅有 AssetInstance 的所谓“可使用对象”。

建议新增 `src/systems/` 下的纯逻辑模块：`EntityRegistry.js`、`InteractionSystem.js`、`CollisionWorld.js`、`RoomSnapshot.js`、`GameplayEvents.js`、`AssetValidator.js`。不要求一次推翻原项目；先为现有 `VoyageM1` 提供适配器，再按系统逐个迁移。

```text
Input (本地按键/设备) → ClientIntent(sequence,tick,entityId,verb,payload)
 → Permission & reachability (房主/服务器) → Physics/Rules (固定 tick)
 → Authoritative Event → State replication → Animation / FX / Sound / HUD
                             ↘ QA trace(id,tick,owner,old,new,evidence)
```

### 3.2 必须保持的不变量

1. 世界坐标 W、船体坐标 S、骨骼坐标 B、相机坐标 C 必须分别命名。固定船体对象 `P_world = T_ship × P_local`，不得在船转向时重新拼世界坐标。
2. 船体唯一物理位姿：`BoatController` 主状态；人站船上在船局部空间运动，继承甲板位移与角速度；水位从同一海面查询接口采样。
3. 角色不可因视觉模型不规则而穿透：以胶囊/凸体为接触体、角色头/脚与视觉模型一致；穿越门时需有完整扫掠形状检测。
4. 任何客户端都不能凭自己发的“命中”事件直接增加钱、伤害或物品；服务器/权威主机做合法性验证、时间与距离检查、去重。
5. 交互结束以后必须明确释放焦点、岗位占用、held item、正在播放的动作和相机控制器，不得残留热键状态。

### 3.3 更新顺序（建议固定 60 Hz 玩法）

`collectInput → networkIntent → resolveClaims → worldClockWeather → shipForces → integrateShip → moveDeckPlayers → collisionResolve → weaponAndHit → floodingAndFire → questsAndInventory → publishEvents → animate → audio → render`。对现有 `BoatController` 内部 120 Hz 子步积分保留；避免先移动玩家、后移动船导致脚底抖动。

**建议预算**：游戏逻辑固定 60 Hz；主船操控输入到视觉回馈的典型延迟 ≤ 100 ms（本地），90 分位 ≤ 150 ms；60 FPS 模式一帧渲染 16.7 ms 内；网络物理更新 10–20 Hz + 客户端插值。以上是目标阈值，需实测报告；低配设备另定动态画质档。

## 4. 原船模型、空间尺度与碰撞网格（P0）

### 4.1 模型资产作为唯一几何基准

目前主要是 `public/models/stormwake_v54/dutch_ship_lower_hold.glb`，历史资产有 `stormwake_v47/dutch_ship_medium_pbr.glb`、`stormwake_v50/captains_quarters_access.glb` 等。主船和舱室需要建立**资产注册表**，记录原始来源、派生链、轴向、scale、原点、边界盒、是否带蒙皮、LOD、碰撞层、授权。并在 import 时校验当前被引用的版本，禁止新旧网格同时显示。

`HeritageDeck.js` 已提供 `deckHeight`/`measuredFloorAt`，但它是地板高度推断，不是所有墙、栏杆、楼梯与动态物的完整碰撞。建议从构造后的网格生成**静态三角形 BVH 或二维楼层栅格+封闭壁体凸体集合**，将可行走面和禁止穿越面分别烘焙。用于修复模型的切口应同时更新视觉网格、碰撞网格、遮挡体积与导航连接，而不是只改其中之一。

### 4.2 角色尺度审查与通行规范

在当前源码，`DUTCH_SAILOR.height=.96`，原船尾门通行高约 `1.094`，这是可精确复核的代码值。若做《盗贼之海》式成年海盗，应**先决定全项目统一物理尺度**，再审查船体比例；不能仅为穿过门把角色整体缩小到失真比例。设计目标：默认海盗身高 1.65–1.85 m，胶囊半径约 0.28–0.35 m，典型舱门净宽 ≥ 0.85 m，主通道净高 ≥ 1.90 m；若保留原史实低门，则提供真实蹲身 1.20–1.35 m 的碰撞姿势，明确有动作及 camera-height 过渡。所有尺寸均需相对船原始美术单位重新测量，不能直接填进当前代码。

**门口改造规则**：允许对 CC0 船体原始副本做可追踪重拓扑，保留设计风格；门框切割后补边、法线、UV、厚度；动态门板独立轴心；门扇 Sweep 轨迹做阻挡；穿门角色胶囊在每次移动时扫掠，碰撞门框、屋顶、地板和舱内桌椅。遮挡视野不是解决碰撞的方式。

### 4.3 全船碰撞层规范

| 层 | 内含 | 检测关系 | 防穿模策略 |
|---|---|---|---|
| `WALKABLE_STATIC` | 上下层甲板、楼梯、船长室地板 | 角色胶囊 foot cast | 单向支撑 + 坡度上限 + 不可跨越舱口 |
| `SOLID_STATIC` | 舷侧、梁柱、栏杆、门框、船舱家具 | 胶囊 sweep + slide | 不能用单点 y 高度替代完整接触 |
| `KINEMATIC_DOOR` | 船长室门、货舱盖 | 相对扫掠碰撞 | 阻挡检查 + 防夹状态 + 网络一致 |
| `DYNAMIC_PROP` | 木桶、宝箱、炮弹、吊钩 | 碰撞体 + 抓取插槽 | 取放时暂时切换物理归属，释放后不陷入甲板 |
| `SHIP_HULL` | 船体外壳、龙骨 | 世界场景/船只/海怪 | 外部接触不影响内部角色无故弹飞 |
| `WATER_QUERY` | 波面与海底 | 采样，不直接充当室内墙体 | 干舱水面不来自外部无限海面网格 |
| `TRIGGER` | 岗位、任务、入口、伤害区 | 不施加物理推力 | 必须和实物相邻且有可视证据 |

### 4.4 甲板→船长室→货舱的完整路径

分别维护 `DeckSurfaceGraph`：主甲板 D0、船尾上甲板 D1、船长室 C0、货舱 H0、桅杆平台 M1。节点是物理可站立平台，边是**真实门洞、梯子、台阶、舱口**；只允许通过已存在边来切换层级。角色入舱时由其扫掠轨迹决定 `deckLayer`，不要先切标签再传送到不连续地形。每条边具有：入口体积、通行姿势、局部登梯轴、最小净空、落脚点、多人数冲突规则与退出反向路径。

`ShipLadder.js` 中已有 `beginShipClimb`、`beginCabinDoorEnter/Exit`，下一步需要将其从“按固定曲线移动位置”升级为**动画根运动与碰撞一致的受约束攀爬**。动画不能让手抓空气；应检测左右手触点与每级横档对应，脚踩实板才退出梯子模式。

**验收**：两人对向通过同一门，门扇开闭 20 次，船分别左/右倾 15°，摇摆波浪中上下梯 20 次，服务器主机切换 2 次；均不得穿梁、头穿屋顶、落地钻甲板或退出卡死。无合法落脚位置时停留在梯上给反馈，绝不强行穿越。

## 5. 海水与干舱：必须拆成三套互不污染的水系统（P0）

### 5.1 当前风险来源

`App.js` 在 `isDryHoldCamera()` 返回真时设置 `this.ocean.visible = !dryHoldCamera`，同时关闭浪花/喷雾，使用了依赖视角的全世界隐藏策略。`WaterMaterial.js` 存在船体局部 `discard` 排除体积和 `hullMask` 屏幕深度判断。两种思路混用，容易造成：船舱里出现水线、舱窗外突然看不见海、切换舱层一帧闪烁、船摇摆时遮罩缝隙或误删舷外波浪。当前截图已出现值得回归的横线；其真正渲染通道必须通过隔离通道截图来确定。

### 5.2 目标设计：Ocean / Hull Interior / Bilge

1. `OceanSurface`：世界海面 FFT、白沫、反射、风浪，始终存在于世界；窗外可观察，不作为干舱里的液面。海浪高度由同一 `WaterQuery` 提供给船体物理与角色游泳。
2. `DryHullVolume`：**物理封闭船舱负体积**。使用烘焙船体 SDF/闭合凸体 + stencil/depth 的可验证裁剪，使海面片段在干舱体积中被丢弃，但在舷外、窗外、舱口外仍显示。船的位置、横摇、纵摇和波峰高度每帧进入同一变换矩阵。
3. `BilgeWater`：真实进水后的船舱积水网格，存在各独立舱室的底部，只随 `ShipDamage.water` 或多舱水量变化；0 漏水时无网格，进水时才出现反光、涟漪、漂浮物与角色水中阻力。

**禁止回退**：禁止以 `ocean.visible=false` 全局开关作为最终方案，禁止通过把海面颜色改黑来“隐藏水”。必要时可以保留调试开关隔离渲染原因，但不得发布为正式修复。

### 5.3 推荐帧序

```text
A. 深度预通道：ship opaque, room walls, doors, props
B. Hull-inside stencil / SDF：闭合体积+可见舱口或窗洞
C. 世界海洋通道：绘制所有外部海面；舱内排除，窗外保留
D. Bilge local surface：仅 draw 舱内积水，按各舱水位裁切
E. Translucent foam / spray / wetness：根据所在位置和开启窗口可见性绘制
F. Post effects：相机真实浸没于 Ocean/Bilge 时启用对应后处理
```

**关键裁剪测试**：空舱静水、空舱浪高 5、满舱漏水、开窗、开门、从甲板低头看舱、从舱内看向水面、站船外看舷板、跨舱门连续帧，至少 9×昼/夕/夜×左右倾角 = 54 组关键帧；每组保存 RGB、深度、遮罩、波面和 bilge 通道。裁剪必须连续，不可出现贯穿墙面的白线。

### 5.4 进水量不是“海面染色”

`HullCompartments.flowRate` 已以破口半径与入水深度计算灌水，但 `ShipDamage.water` 仍主要是单个归一化值。建议升级为 3–5 个舱段的体积积分，船首/中部/船尾水量不同，漏水先入相应舱段，舱门开启时按流量互通，积水改变浮力重心并可观察，修理破口停止新入水但不瞬间清空旧水。保留单一 HUD 总量作为汇总值。

## 6. 船舶运动：现有积分保留，建立物理可追踪链

### 6.1 当前实现和改造界线

`BoatController.step()` 中确有样本浮力、局部横向阻力、推进、转舵、接地、海漩吸力与半隐式积分，积分子步为 `1/120 s`；不是纯粹传送动画。航海模式把帆力叠加到推进力上，`VoyageM1` 的部分路径还把辅助动力设为 0。**建议增强而非整套删除**：模型几何/重心与质量的一致性、锚链张力、船首浪峰冲击、船上人体平台动力学是当前优先级。

### 6.2 舵、帆、风、龙骨、锚的职责

| 控制器 | 输入 | 物理实际结果 | 可视/音效必须绑定 |
|---|---|---|---|
| 舵轮 | 抓取后 A/D 或鼠标左右旋转 | 舵角上限、航向角速度、速度损失 | 轮轴旋转、舵叶旋转、居中咔嗒、受力阻尼 |
| 主帆/前帆 | 按住 W/S 调帆高，A/D 调帆角 | 投影面积×风向×风速确定动力 | 绳索收放、帆布卷曲/张紧、帆索拉扯 |
| 锚机 | 抓四个独立把手，按住 W/S | `anchorTravel` 连续变化，链长/锚接触海床状态 | 全体共享轮转、铁链行进、锚体落海 |
| 锚 | 进入已接触海床状态 | 张力/摩擦抑制位移；急转受限制 | 链绷紧、船速降低、拖锚警告 |
| 舵/锚损坏 | 炮击、海怪冲撞 | 操作阻力升高或暂不可用 | 裂纹/火花/折损声与修理互动 |

### 6.3 锚的有形机理

建议状态机 `STOWED → LOWERING → FALLING → SEABED_CONTACT → HOLDING → DRAGGING → RAISING → STOWED`。`anchorTravel` 只表达链行程，不再直接代表“船突然完全被锁住”；若距离浅水海床达不到锚深，进入 `NO_BOTTOM_CONTACT`，船可小幅漂移。力的简化实现为分段弹簧阻尼：`F_chain = -k max(0,L−chainLength) n − c (v·n)n`，限幅并施加船体相应附着点力矩。先在准静态场景校准，再加入海床条件；不要求重量链逐环刚体模拟。

**操作安全**：1 人与 4 人收链速度比建议约 1:2.2–2.8（不是四倍无限制），放开 W 后旋转停止；退出岗位不得继续锁输入；锚卡住时发出声响/提示；落锚以前船绝不能因 AI 自动开航。现实体验以“可观察过程和力学反馈”为基准，不强求海事级精确仿真。

### 6.4 甲板人物在六自由度移动船上的稳定性

使用船局部胶囊来做甲板碰撞，世界坐标渲染时乘上船位姿；角色跳起时保留船对角色的线速度 `v_ship + ω×r`，落回甲板进行接触约束和摩擦，避免跑动时脚沿甲板滑动；进舱时相机跟随局部坐标，滚转通过缓动限制眩晕。船体剧烈碰撞才进入摔倒/跌海，并由物理冲量而不是随机阈值触发。

### 6.5 船体接触与约束

禁止“接近岛屿就缩放/传送船身”；船对礁石、浅滩、码头桩和另一条船的碰撞应由碰撞点法线、相对速度产生冲量。定义软/硬接触和刺穿回退阈值。撞码头需可见撞击效果，不能整船瞬移；同时确保船头外壳封口在任何相机角度都不透视。

## 7. 岗位交互、输入仲裁与锚机故障修复（P0）

### 7.1 修复 `interact_anchor` 的完整排查图

`AutoQA.go('anchor')` 把玩家放到 `stationLocalMeters(anchor)` 附近；`VoyageM1.getNearbyCandidates()` 生成所有岗位/船舱/道具候选并赋予不同 priority；`InteractionDirector.select()` **按 priority 优先，距离次之**，`dispatch()` 消耗 E；`ShipNetBridge.claim()` 在联网下等待 `station_update`；`ShipStations.claim()` 管理占用。**只有观察这整条链的事件日志才能确定是否真的接到了锚机。**

需要新增 `qa.interactionTrace()`：`{tick,playerLocal,rayHit,availableCandidates,selectedId,inputConsumed,claimSent,ack,finalStation,focusOwner}`。一旦 E 没有进入锚机，立即记录“焦点被遮罩拿走”“范围不足”“被较高优先级候选抢走”“房间拒绝”中的具体原因，不再输出模糊的 None。

### 7.2 从距离+优先级改为视线可见的实体选择

交互筛选先进行：同层可达 → 距离（默认 1.6–2.2 m，可随岗位不同）→ 视线球锥/raycast → 无遮挡 → 输入模式允许 → 服务器授权 → 再排序。鼠标准星直接指向物体时，命中对象优先；仅脚边多个可交互物才用优先级。可通过鼠标滚轮/Tab 在候选中切换，不允许不可见的高优先级按钮抢走玩家正在按的锚机。

### 7.3 岗位状态规范

`FREE → HIGHLIGHTED → REQUESTED → CLAIMED → OPERATING → RELEASING → FREE`；另外 `DENIED_OCCUPIED`、`OUT_OF_RANGE`、`DISCONNECTED`。服务器控制 `CLAIMED`；客户端在 `REQUESTED` 时不擅自转动绞盘，若 500 ms 内无 ACK，显示等待/重试，1.5 s 超时退出。解除 E 必须和进入 E 明确分离（按 E 退出、Esc 强制退出）；移动键在操作模式不再驱动角色走动。

**锚机工位**：四个物理把手绑定到真实绞盘的旋转局部坐标；旋转后交互点也随之变换，不能四个虚拟锚机定死在直角坐标。多人占不同把手时按同一方向推，反向推发生有界抵消；离岗保持锚机状态，不得扣留玩家。

### 8.2 道具是真实物件而非装饰

每个桶、炮弹、修船木板、望远镜、宝箱应具有：世界唯一 `objectId`、实体碰撞、质量/尺寸、可拿取 socket、抓取距离与射线、与左右手的动画、携带速度限制、可放置 surface、掉落冲量、服务器 ownership、掉线恢复、储物数量显示。`Take → InHands → Stow / Use / Throw / Drop` 五类操作都必须可被 QA 复现。

禁止无实体的 UI 补给：从弹药箱取炮弹时箱内数量减一、玩家手中出现模型；装入炮口时手中模型消失，炮膛物理状态变为 LOADED；开炮以后炮口有弹道，服务器资源消耗一次；玩家不能一边拿两门炮弹一边无限携带。

## 9. 武器、舷炮、射击、破坏和修复闭环

### 9.1 舷炮状态机

`IDLE_EMPTY → HAND_LOADING → RAMMING → LOADED → AIMING → FIRING → RECOIL → COOLDOWN → IDLE_EMPTY`。装填时需要炮弹在手、到炮尾的位置与装填动作；炮身可转动且有机械限位，炮口朝向与弹道初速度必须一致。后坐力不应只在相机做抖动，应让炮架、烟雾和船员手部都收到可见响应。若 `COOLDOWN` 未完成，不可连发。其他客户端必须看到同一次射击与炮口动画。

### 9.2 球形物理弹道与船体撞击

初始速度来自炮口世界 transform，位置 `p(t+dt)=p+v dt`，速度包含重力、可选风阻，命中使用 swept-sphere test，避免高帧间速度穿过船壳。需要区分 `hull` / `mast` / `capstan` / `helm` / `sail` / `environment` / `creature`，不同目标对受击动画、损坏、修理通道产生不同后果。炮弹落水只有浪花，不能凭接近船就扣血；破口只出现在被击中、可以接近修理的船壳区域。

### 9.3 船损、水损与人类可感知的反馈

破口渲染为船壳局部缺损/贴木板修补，水流从真实位置涌入相应舱室，船内声音随流速增加；船速与航向受进水质量影响；多个水桶舀水需协同，舀出水必须在船外完成倒水动作（舱内错误倒水不应降低船内水量）。木板耗材减少一次，修补有进度与中断；修补只终止该洞入水，已有水仍需舀出。

### 9.4 各武器真实行为

捕鲸叉：拉弦/抛射/飞行/入体/缆绳拉紧/断裂；长枪：装填、瞄准、射击、回弹；手枪：击发与换弹；水炮/声波（奇幻装备）：明确资源与射程、碰撞、技能冷却；望远镜：真实 FOV 过渡且遮罩不遮目标。严禁用“点击播放粒子并直接扣血”冒充命中。

## 10. 角色、AI 船员和肢体动画

### 10.1 动画资产与接触质量

现阶段联机角色已有分段四肢程序化动画，但不等于完整骨骼动作。建议构建 `CharacterMotionGraph`：Idle、Walk、Run、SprintStop、Jump、Fall、Land、ClimbLadder、CrouchDoor、GrabAnchor、TurnCapstan、HaulRope、SteerHelm、AimCannon、LoadCannon、CarryChest、Repair、Bail、Swim、Hit、Death、Recover。每个状态含进入条件、动作中可移动范围、手脚接触点、可打断窗口、网络同步的 stateId/timePhase 与退出 cleanup。

足底锁定用 two-bone IK，手部操作用目标 socket IK；船体晃动经局部稳定器处理，避免人物明明站在甲板却飘到空气中。轻量 WebGPU 设备可降低远景 IK 更新频率，但近景同船角色不能用“浮空木偶”替代。

### 10.2 真人/AI 优先权与可见行为

AI 水手可以在无人时接 helm/sail_main/cannon 岗位，但玩家进入工位后 AI 在 0.3 秒内释放；AI 不能隐形自动起锚。AI 需要**真实移动到岗位**：通过甲板导航网格走近、手抓真实道具、站定执行动作；若路被玩家堵住，转向、等待、重新规划。任务日志记录 “哪个 AI 于何时进入/退出哪个岗位”。若未实现动作，应标记为 WIP 而非 HUD 虚报“AI 在岗”。

## 11. 多人联机：从“看见彼此”升级到“同一个物理世界”

### 11.1 已有基础与实际空白

V58 已测到两独立浏览器加入一个房间、位置变化和世界时钟/天气时轴接近一致。`ShipNetBridge` 以房主发送 `ship_state_host`，含船位姿、帆、锚、伤害等；但原工程 `README_STORMWAKE_V57...` 已承认部分背包、民居、陆地 NPC 仍是本地逻辑。下一步应做**逐实体网络所有权表**，不能把“世界时钟一致”宣传成完整多人玩法完成。

| 状态 | 权威源 | 同步策略 | 冲突/断线行为 |
|---|---|---|---|
| 船刚体、风/水波相位 | 房主模拟+服务器时钟 | 10–20 Hz 快照、客户端插值 | 房主迁移时恢复最新快照并保持速度 |
| 岗位占用/锚链/炮装填 | 服务器仲裁，房主执行 | 命令序列+状态事件+周期全量 | 离线释放，过期输入丢弃 |
| 角色动作及相对甲板位置 | 玩家意图+房间校验 | 位置带 `shipId/localPose` 和动画阶段 | 超距纠正，重连恢复当前动作 |
| 船破口/进水/火灾 | 权威房主 | 精确 event log + 快照 | 命中不可重复；Late join 重建洞口 |
| 宝箱/货物/金币 | 服务器事务 | item version / ownership / inventory diff | 只发一次钱；断线货物仍在船上 |
| 海怪/幽灵船 AI | 权威房主 | AI 状态/随机种子/命中事件 | 房主迁移时保留目标、血量、技能阶段 |
| 时间、天气、雷暴 | 服务器 `SharedWorldClock` | 一致的种子、绝对时刻 | 迟到玩家同时间、同天气场 |
| 门、舱口、灯笼 | 服务器/房主可验证 | 较低频率事件+全量恢复 | 新人进入得到当前开合和亮灯状态 |

### 11.2 真实多人时序

**例：A、B 起锚**：A 按 E 请求占用 `anchor`；服务器回 `station_update(A)`；B 请求 `anchor_2`；服务器授权；A、B 每 50–100 ms 发送各自 W/S 轴值；房主固定 tick 汇总操作手数；统一更新 `anchorTravel` 与 `anchorCrankTurns`；服务器同步状态；所有客户端按同一曲线渲染铁链、绞盘；A 掉线，B 继续操作，`anchorHands` 从 2 变 1。任何客户端不得各自私下修改锚机位置。

**例：B 修船**：B 客户端发 `{holeId, toolId, action, inputTick}`，主机验证 B 在洞口旁、手中木板已持有、未在船外、不在冷却；提交 `PatchStarted`；2.0–4.0 秒有效连续操作后 `PatchCompleted`；全房间移除洞口流量并播放修补动画；断线时有确定的中断处理。

### 11.3 对抗网络异常

必须测试：50/100/200 ms 延迟、2/5/10% 丢包、乱序、重复包、房主拔网线、双玩家同时拾取同一宝箱、炮弹重复包、重连后另一玩家仍在舵位、房主迁移时海怪正攻击。指标建议：没有资源复制或负库存；角色短暂纠偏但不可持续漂移；船与角色不大规模跳帧；房主迁移后 3–5 秒内可继续操控（初始目标）。

## 12. 海域、天气、海怪和岛屿：针对现有功能的修复

### 12.1 远海的实际空间逻辑

`OffshoreField.js` 定义近岸商路、外海风暴、幽焰舰队、龙卷、东部深蓝等区域，`weatherAt(x,z,time)` 以位置/时间计算天气，`vortexForceAt` 将漩涡加速度引入船积分。无需再添加漂浮的视觉圆圈来表示区域。应在进入区域前 300–600 m 出现可感知的云墙、浪向变化、雷声、风帆拉力变化；同一房间每个客户端得出同一危险度，港口为真正的风暴缓冲地带。

`AutoQA.go(open_sea)` 不得固定传送到一个未经地形检验的点；从 `OFFSHORE_SITES` 周边采样，验证当前地形 `heightAt(x,z)<-6` 且船横向 30 m 安全半径无礁石，再移动并验证是否真的激活目标 AI/天气。

### 12.2 GhostFleet / 龙卷 / 陆地 Boss

幽灵船：要拥有航行导航、避碰、追踪、真实炮口、炮弹与绿焰灯光，不能只有船模型漂移。龙卷：粒子/体积云与船体加速度场使用同一个中心、半径和时间函数，风雨随逼近连续增强。陆地 Boss：若出现巨大光团，应分开审查 `actor GLB 加载 → rig/skin binding → body mesh visibility → glow post FX`；不能用放大光球替代网格。每个实测镜头至少存 3 个视角并检查模型已完整加载。

### 12.3 鲨、乌贼、三头龙、利维坦

已存在 `TitanAI` / `TitanSkeleton` / `LeviathanRig` 等模块；首轮先抽取一个海怪（建议巨型乌贼）验收真实触手端点接触和甲板受力，再扩展全部怪物。须用骨骼 tip / mouth socket 到船壳表面最短距离做真实命中门槛；未接触不允许直接扣血；碰撞时既有局部变形/打击动画，也有相同权威事件作用于船物理；网络上所有玩家看到同一命中时刻。

## 13. 美术与 UI：避免“看似很多但真实体验差”

### 13.1 画面风格目标

学习《盗贼之海》的**明快海盗冒险、清晰轮廓、强烈色彩对比、天气戏剧性**，但保留 STORMWAKE 自己的主船和海域世界观；不复制 Rare 的场景、UI 图标、音乐与专有角色。优先保证靠近相机 0–5 m 内的木材、铁件、船帆、绳索、铆钉、灯罩真实感，再做远景特效。当前船长室出现英国米字旗图样：是资产审美审查事项，是否保留按项目世界观决定；现有 CC BY 4.0 资产必须注明来源及修改。

### 13.2 光照、材质和水体视觉

统一材质 PBR 数据域：albedo 为 sRGB，normal 与 rough/metal 为线性，切线正确；贴图一套完整的 AO/Roughness/Metal 不得用错误通道。日落、阴天、月夜和船灯须有独立曝光目标；船灯发光几何体必须对应点光源，货舱需有防黑暗的灯具，但不能日间也全黑。曝光不能在进入暗舱时瞬间拉满或拉黑，建议 0.5–1.5 秒自动适应，可配置降低闪烁。

### 13.3 UI 重构

当前截图中左栏占据大面积，顶中间任务文字和全屏开场叠加。建议游戏态常驻 HUD 只显示：小型指南针、当前工具与弹药、血量、船损告警、情境 E 操作提示、船员位置提示；详细任务/装备/调试数据只在 `Tab`/地图页/开发者模式中显示。动态提示置于被看向对象旁，超时消失；任何屏幕空间面板都不得覆盖中心准星与操作物。

## 16. 核心数据协议与示例

### 16.1 规范对象

```ts
interface ObjectState {
  objectId: string;  // across reconnect stable
  type: 'helm'|'capstan'|'cannon'|'door'|'item'|'breach'|'creature';
  shipId?: string; localPose?: {x:number;y:number;z:number;yaw:number};
  revision: number; tick: number; ownerId?: string;
  phase: string; progress?: number; health?: number;
}
interface GameplayIntent {
  intentId:string; playerId:string; targetId:string;
  verb:'claim'|'release'|'use'|'aim'|'fire'|'carry'|'repair'|'bail';
  clientTick:number; payload:Record<string,number|string|boolean>;
}
interface GameplayReceipt {
  intentId:string; accepted:boolean; reason?:string;
  serverTick:number; objectRevision:number;
}
```

### 16.2 网络一致性/幂等

同一个 `intentId` 重试必须返回相同结果，不能重复消耗炮弹、木板、金币；版本号只接受递增；角色若距离目标超过可达边界则拒绝 `use`。所有物品入库/出库使用原子事务，单人离线与联机使用相同规则，区别仅在权威执行端。

### 16.3 碰撞和渲染不变量脚本

```text
for every rendered ship-interior frame:
  assert(playerCapsule does not penetrate SOLID_STATIC)
  assert(playerFeet supported OR playerState is climb/jump/fall)
  if compartment.dry && breaches==0: assert(bilgeVolume==0)
  assert(oceanSurface clipped only inside sealed volume)
  assert(outsideOcean remains visible through valid openings)
for every object interaction:
  assert(interactable.visible && raycastUnblocked && targetWithinReach)
  assert(acceptedAction produces authoritative state/event/feedback)
  assert(replayed intent has no additional side effect)
```
